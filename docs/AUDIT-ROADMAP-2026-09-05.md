# saikai 監査と今後の方針（2026-09-05）

後続の議論で、名前付き作業セットに加え、同一プロジェクトでClaude/Codex/Antigravityを
選んで使う小さなランチャーとMarkdown引き継ぎを検討対象とした。
その[実装計画](superpowers/plans/2026-09-05-project-agent-switcher.md)を作成済み。
以下の監査結果は維持しつつ、Codex対応の判断は「遠隔操作の再実装」と
「公式CLIを利用するランチャー」を分けて読む。新機能はまだ未実装。

## 判断

大きな機能追加は一度止め、復帰作業に役立つ小さなOSSとして保守することを推奨する。
所有者の実際の用途は、SSH端末を再起動した後に複数のClaudeセッションを再開し、
その後はClaude Desktopから操作すること。saikaiの使用時間が短いこと自体は問題ではない。
価値は「復帰に必要な時間と操作を減らせること」にある。

公開OSSとしての成長は、この用途での有用性を公開した結果として狙う。
汎用のエージェント管理画面や独自リモート操作環境を拡張し続ける投資は、現状では勧めない。

## 監査対象と変更

`git pull --ff-only` 後の `e36f904` を基準に、履歴・起動の境界、ペイン復元、
端末の起動時描画を重点確認し、既存テスト全体を実行した。
実ユーザーの会話を起動・変更する検証やSSH先での試験は実施していない。
全コード経路・全OSの安全性を保証する監査ではない。

修正した内容:

1. **復元の成功表示が実態と違う。** 容量制限などで起動を拒否された場合や、
   別ウィンドウのセッションを開く確認が保留中でも「reopened」と数えていた。
   起動受付・拒否・確認待ちを戻り値で区別し、非同期の起動受付は「queued」と表示する。
2. **壊れた復元データで処理が中断する。** 保存データ全体が数値の場合や、
   未索引セッションのcwdが数値の場合にTypeErrorとなる。型を検証し、
   不正な項目を飛ばして残りの復元を続ける。
3. **白黒表示で起動中・起動失敗のペインがクラッシュする。** スタイル未指定の
   Segment/空行をTextualのMonochromeフィルターが処理できなかった。
   空のStyleを明示し、エラー行と空行を描画できるようにした。
4. **READMEの公式機能比較が古い。** 英日両方で、公式には検索・プレビュー・
   プロジェクト横断表示がないという記述を訂正した。

`tests/test_restore_audit.py` に6件の回帰テストを追加。
修正前は6件とも失敗し、修正後は通過した。端末の既存concurrencyスイートも修正後に通過。
PTYの所有権、ロック、終了処理、Claudeの履歴ファイル形式は変更していない。

最終検証は `uv --cache-dir .audit/uv-cache run --no-sync python` で既存の仮想環境を
使用した（Textual 8.2.8 / Rich 15.0.0 / pyte 0.8.2 / pywinpty 3.0.5）。
`py_compile` は通過。`tests/test_*.py` 全23ファイルを実行し、21ファイルが終了コード0、
ミラーの `test_mirror_hub.py` と `test_mirror_input.py` の2ファイルは失敗した。
端末のconcurrency、resource bounds、protocol、watchdog、実PTYテストは通過。
Windowsのため一部POSIX固有ケースはスキップされている。

残る2ファイルではlocalhostのHTTP応答が `WinError 10054` で切断され、
入力テストではHTTP 413を期待する箇所が接続エラーとなった。
制約外での再実行でも発生し、saikaiを一切含まない `http.server.ThreadingHTTPServer` と
`urllib.request` だけの対照試験でも、100 KBの応答を読み取る途中に同じ切断を確認した。
saikai固有の不具合とは断定できない一方、環境側の具体的な原因も未確定。
応答切断を許容するようにテストを緩めてはいない。リリース前には正常な通信環境で
この2スイートを通す必要がある。全テスト成功・リリース可能とは判定していない。
実行ログはローカルの `.audit/*-final.log`、対照試験は `.audit/socket_probe.py` にある。

## 公式機能との差分

| 項目 | 確認した公式機能 | saikaiへの含意 |
|---|---|---|
| Claudeの履歴選択 | `claude --resume` に検索・プレビュー・`Ctrl+A` の全プロジェクト表示 | 横断一覧だけを差別化として宣伝しない |
| Claudeの実行管理 | `claude agents`、`attach`、`respawn`、JSON一覧 | 同種の監督画面をさらに拡大する優先度は低い |
| Claude Remote Control | サーバーモードは同じディレクトリで再起動すると配下のセッションを復元できる。ただし停止後およそ4時間などの条件がある | 一括復元の必要性も実際の使い方とバージョンで比較する |
| Claude Desktop | SSH先のLinux/macOSで動かす機能がある | Desktopへ直接接続できる範囲を先に確認する |
| Codex | SSH接続先のapp-serverをアプリが起動し、サーバーが複数の会話を扱う | Codexの会話ごとにPTYを立ち上げる機能を先に作る必要はない |

Claudeのサーバーモード復元は、個々に `claude --remote-control` や `/rc` で
開始したセッションの一括復元と同一ではない。後者の会話再開には `--resume` 等を用いる。
`claude respawn --all` も「停止済みを含むすべての過去会話を復元する」コマンドではない。

- [Claude agent view](https://code.claude.com/docs/en/agent-view)
- [Claude Remote Control](https://code.claude.com/docs/en/remote-control)
- [Claude Desktop](https://code.claude.com/docs/en/desktop)
- [Codexのリモート接続](https://learn.chatgpt.com/docs/remote-connections)

## Codex対応の考え方

このWindows環境のCLIは `codex-cli 0.144.5`。
`codex remote-control --help` と `start --help` に、remote controlを有効にした
app-serverデーモンの起動が明示されている。起動自体は実行していない。

通常の対話型 `codex` を一つ起動すれば全会話が遠隔操作可能になる、という意味ではない。
接続先のサーバーに保存された会話を一覧し、必要な会話を `thread/resume` で読み込み、
ターンを実行する。保存履歴の再開と、別CLIプロセスで実行中の処理の引継ぎは区別する。
表示範囲にはSSHユーザー、CODEX_HOME、プロジェクトやアーカイブの条件が関わるため、
「すべてのセッションを自動的に操作できる」とは約束しない。

リポジトリにはCodexProviderの起動契約があるが、履歴統合は未完成でユーザー選択不可。
これは今回の目的では直ちに埋める必要のある欠陥ではない。
まず公式SSH接続で既存のCLI会話が表示・再開できるか確認する。
それで足りるなら、saikai側のCodex実装は不要。

## ロードマップ案

### 今すぐ: 安定化と説明の修正

今回の不具合修正を検証する。主用途である復元手順を短いドキュメント・動画にする。
宣伝文句の候補は「SSH再接続後、使っていたClaudeの作業セットをまとめて再開」。
現時点で未実装の自動復旧、SSH切断後の永続稼働、Codex統合は宣伝しない。

### 次の実利用2〜4週間: 公式機能との比較

新機能を作る前に、実際の再接続・再起動時に以下を記録する。
個人用の手元メモでよく、製品へのテレメトリー追加は不要。

- 戻したいセッション数と、実際に戻せた数。
- 操作開始からDesktopで使えるまでの時間と手動操作数。
- 再開できなかった理由、重複起動、作業フォルダの誤り。
- Claude公式サーバー復元またはCodex公式SSH接続だけで完結したか。

### 不足が繰り返し確認できた場合だけ: 小さな追加

優先候補は、名前付き作業セット、失敗した項目だけの再試行、実行前の一覧確認。
Codexはまず接続先のバージョン・サーバー状態・接続案内の支援を検討する。
独自の会話ビューやリモート制御プロトコルの実装は、公式接続では満たせない用途が
確認されるまで着手しない。これらは提案であり今回の実装ではない。

新たなミラー機能、端末エミュレーター機能、複数プロバイダー統合、
自動コンテキスト再構成は当面追加しない。現在のランタイムはコメントを含め約2.5万行で、
とくにPTYとミラーは継続的な互換性・セキュリティ検証を要する。
分割リファクタリング自体も目的化せず、実際の修正箇所から必要に応じて行う。

## マーケティングと更新停止の判断

対象は「複数のClaude CLIセッションを使い、復帰後の操作はDesktopで行う人」。
一つの実例を短い動画とREADMEの手順で公開し、同じ困り方をする利用者から反応を得る。
スター数やTUIの滞在時間より、再利用・復元成功・保守負荷を見る。
外部への投稿や告知はこの監査では行っていない。

自分の復帰に役立つ限り、小さく保守する。公式機能だけで不足なく回る状態が
実際の複数回の復帰で確認できたら、新機能を凍結し、互換性・重大不具合修正だけにする。
自分も他の利用者も固有機能を必要としなくなった時点で、移行案内を残してアーカイブを検討する。
利用者増加のためだけに維持費の大きい機能を追加する必要はない。
